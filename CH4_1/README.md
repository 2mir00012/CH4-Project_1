# MIR Number Baseball

Unreal Engine 5.6과 C++로 구현한 멀티플레이 숫자 야구 게임입니다. 서버가 생성한 정답을 플레이어가 번갈아 추측하며, 각자 3회의 기회 안에 먼저 정답을 맞히면 승리합니다.

필수기능으로 채팅과 숫자 판정, 시도 횟수, 라운드 종료를 구현했습니다. 이후 도전기능으로 턴과 제한 시간을 적용하고, 누적 승수·준비 및 시작·전광판 UI를 추가했습니다.

## 1. 개발 환경 및 실행 방법

| 항목 | 내용 |
|---|---|
| 엔진 / 언어 | Unreal Engine 5.6 / C++ |
| 개발 도구 | Visual Studio 2022 |
| 프로젝트 | `CH4_1.uproject` |
| 레벨 | `Content/MNB/Maps/MIR_Number_Baseball.umap` |
| 접두사 | `MNB` — 클래스 종류에 따라 `AMNB`, `UMNB`, `FMNB` 사용 |
| UI | UMG / C++ 위젯 |
| 기본 시연 구성 | 전용 서버와 클라이언트 2개 |

1. Unreal Engine 5.6과 Visual Studio의 C++ 게임 개발 도구를 준비합니다.
2. `CH4_1.uproject`를 우클릭하여 **Generate Visual Studio project files**를 실행합니다.
3. 생성한 솔루션을 열고 **Development Editor / Win64**로 프로젝트를 빌드합니다.
4. 프로젝트에서 `MIR_Number_Baseball` 레벨을 엽니다. GameMode Override가 `BP_MNBGameModeBase`인지 확인합니다.
5. 에디터의 Play 설정을 **New Editor Window (PIE)**, **Number of Players = 2**, **Net Mode = Play As Client**로 설정합니다. Advanced Settings에서 **Run Under One Process**를 해제합니다.
6. 실행한 두 클라이언트에서 각각 **준비하기**를 누릅니다. 두 명 이상이 접속하고 모두 준비하면 게임이 시작됩니다.
7. 자신의 차례에 중앙 숫자 입력창으로 정답을 제출합니다. 일반 채팅은 오른쪽 아래 입력창을 사용합니다. Enter 또는 전송 버튼으로 보낼 수 있습니다.
8. 결과 표시 후 약 3초가 지나면 다음 라운드의 준비 상태로 돌아갑니다. 다시 모두 준비해야 시작됩니다.

## 2. 게임 규칙과 진행 흐름

| 규칙 | 내용 |
|---|---|
| 정답 | 1~9 사이의 서로 다른 숫자 3개 |
| Strike | 숫자와 위치가 모두 일치 |
| Ball | 숫자는 포함되어 있지만 위치가 다름 |
| OUT | 일치하는 숫자가 없음 |
| 시도 횟수 | 플레이어마다 라운드당 3회 |
| 턴 제한 | 기본 20초 |
| 승리 | 자신의 차례에 정답을 맞혀 3S 달성 |
| 무승부 | 승리자 없이 모든 플레이어의 기회 소진 |
| 시간 초과 | 기회 1회 사용 후 다음 차례로 이동 |
| 잘못된 입력 / 일반 채팅 | 기회를 사용하지 않으며 제한 시간도 연장하지 않음 |

예를 들어 정답이 `386`일 때 `368`은 `1S2B`, `123`은 `0S1B`, `145`는 `OUT`입니다.

**접속 → 모두 준비 → 턴 시작 → 숫자 제출 또는 시간 초과 → 다음 턴 → 승리·무승부 → 결과 표시 → 새 라운드 준비** 순서로 진행합니다.

전광판의 **남은 기회 2 / 3**은 앞으로 사용할 수 있는 기회입니다. 기록의 **Player1 [1/3]**은 이미 사용한 횟수입니다.

## 3. 필수기능 구현 과정

### 3-1. 프로젝트와 네트워크 역할 구성

`MIR_Number_Baseball` 레벨을 만들고 게임 관련 클래스와 에셋에 `MNB` 접두사를 적용했습니다. 서버의 GameMode가 정답과 게임 규칙을 관리하고, 클라이언트는 입력을 요청하고 전달받은 상태를 화면에 표시하도록 역할을 나누었습니다.

정답은 GameMode에 보관해 클라이언트로 복제하지 않았습니다. 플레이어마다 달라지는 정보는 PlayerState, 모든 플레이어가 공유하는 라운드 상태는 GameState에 배치했습니다.

### 3-2. 멀티플레이 채팅과 RPC

로컬 PlayerController에서 입력 위젯을 생성했습니다. 채팅을 보내면 소유한 PlayerController의 Server RPC를 통해 서버로 전달하고, 서버가 각 플레이어의 Client RPC를 호출해 같은 메시지를 표시하도록 구현했습니다.

접속 알림은 GameState의 NetMulticast RPC로 전달했습니다. 일반 채팅은 숫자 제출과 분리했으며, 1~200자의 메시지를 허용하고 최근 80줄을 유지하도록 구성했습니다.

**입력 위젯 → PlayerController의 Server RPC → GameMode의 검사·처리 → 각 PlayerController의 Client RPC → 메시지 목록**으로 이어집니다.

### 3-3. 정답 생성과 입력 검사

`MNBNumberBaseballLibrary`에 정답 생성, 입력 검사, 결과 계산을 모았습니다. 1~9 목록에서 숫자를 하나씩 무작위로 뽑고 선택한 숫자를 제거하여 중복 없는 세 자리 정답을 생성했습니다.

입력은 길이가 정확히 3인지, 각 문자가 1~9인지, 같은 숫자가 반복되는지 검사했습니다. `12`, `012`, `112`, `a123`처럼 조건에 맞지 않는 입력은 안내 메시지를 표시하고 기회를 유지하도록 처리했습니다.

### 3-4. S / B / OUT 판정

각 자리의 숫자와 위치가 같으면 Strike를 증가시켰습니다. 위치는 다르지만 정답에 포함된 숫자라면 Ball을 증가시켰습니다. 두 값이 모두 0인 경우에는 OUT으로 표시했습니다.

판정은 서버에서 수행하고, 결과를 플레이어 이름과 사용 횟수에 함께 표시했습니다. 함수 라이브러리는 프로젝트 내부의 C++ 함수 라이브러리로 구성했습니다.

### 3-5. 플레이어별 시도 횟수와 복제

PlayerState에 플레이어 이름, 현재 사용 횟수, 최대 횟수를 저장하고 Replication을 적용했습니다. 유효한 입력을 처리할 때 서버의 `TryUseGuess()`를 통해 횟수를 한 번 증가시켰습니다.

세 번의 기회를 모두 사용한 경우 숫자 입력 UI를 비활성화했습니다. 서버에서도 남은 기회를 검사하여 UI 상태와 관계없이 추가 입력을 차단했습니다.

### 3-6. 승리·무승부·리셋

`JudgeGame()`에서 3S 여부를 먼저 확인하고, 승리하지 않았다면 모든 플레이어의 기회 소진 여부를 확인했습니다. 마지막 기회에 정답을 맞힌 경우에도 승리가 우선 적용되도록 처리했습니다.

`FinishRound()`에서 턴을 멈추고 종료 상태를 설정한 뒤 결과를 전달했습니다. 약 3초 뒤 `ResetGame()`에서 정답을 다시 생성하고 사용 횟수를 초기화하며 라운드를 증가시켰습니다. 최종 구현에서는 리셋 후 준비 화면으로 돌아가도록 확장했습니다.

## 4. 도전기능 구현 과정

### 4-1. 서버에서 턴 제어

GameMode의 `StartNextTurn()`에서 접속한 플레이어 순서대로 차례를 선택했습니다. 기회가 없는 플레이어는 건너뛰고, 유효한 숫자 입력 후에는 `CompleteTurn()`을 통해 다음 차례로 이동하도록 구현했습니다.

클라이언트 UI에서는 자신의 차례일 때만 숫자 입력을 허용했습니다. 서버에서도 현재 플레이어와 턴 번호를 확인하도록 만들어 다른 사람의 차례에 보낸 요청을 거절했습니다.

### 4-2. 20초 제한 시간 동기화

GameState의 `FMNBTurnState`에 현재 플레이어, 턴 번호, 종료 서버 시각, 제한 시간, 활성 여부를 묶어 복제했습니다. 각 클라이언트는 종료 서버 시각에서 동기화된 서버 시각을 빼서 남은 시간을 표시했습니다.

실제 시간 초과 판단은 서버가 수행하도록 구현했습니다. UI에는 남은 초와 진행 막대를 표시하고, 5초 이하에서는 빨간색으로 변경했습니다.

### 4-3. 시간 초과와 중복 처리 방지

제한 시간이 끝나면 `OnTurnExpired()`에서 기회 1회를 사용하고 다음 차례로 넘겼습니다. 잘못된 숫자 입력이나 채팅으로 제한 시간이 초기화되지 않도록 처리했습니다.

입력 요청에 라운드 번호와 턴 번호를 포함하고 서버에서 마감 시각과 제출 여부를 검사했습니다. 턴을 종료할 때 기존 타이머를 해제해 입력과 시간 초과가 겹치더라도 동일한 턴의 기회가 중복 차감되지 않도록 구성했습니다.

## 5. 추가기능 구현 과정

### 5-1. 누적 승수

PlayerState에 `WinCount`를 추가하고 서버에서 승리가 확정될 때 한 번 증가시키도록 구현했습니다. 다음 라운드에서는 시도 횟수만 초기화하고 승수는 유지했습니다. 무승부나 시간 초과에는 승수가 증가하지 않도록 처리했습니다.

누적 승수는 현재 연결을 유지하는 동안의 기록입니다. 재접속은 새로운 플레이어로 처리하므로 승수는 0부터 시작합니다.

### 5-2. 준비·시작·다음 라운드

플레이어별 `bReady`와 공통 상태인 `bWaitingForReady`를 추가했습니다. 두 명 이상이 접속하고 모든 플레이어가 준비했을 때 서버에서 라운드를 시작하도록 구현했습니다.

준비 대기 중에는 준비와 취소가 가능하고, 경기 진행 중에는 준비 상태 변경을 차단했습니다. 결과 확인 후에는 모두 준비 대기로 돌아가도록 구성했습니다. 이전 대기 상태에서 늦게 도착한 준비 요청은 라운드 번호와 `ReadyRevision`으로 구분해 거절했습니다.

### 5-3. 전광판 UI

사직야구장 전광판의 정보 배치를 참고해 게임에 필요한 정보 중심으로 구성했습니다. 전광판 배경 이미지를 적용하고 실제 숫자와 버튼, 기록은 UMG 위젯으로 배치했습니다.

| 화면 위치 | 표시 내용 |
|---|---|
| 상단 | 게임 제목, 현재 라운드 |
| 왼쪽 | 내 이름, 누적 승수, 남은 기회, 준비 버튼 |
| 오른쪽 | 상대 이름, 누적 승수, 남은 기회, 상태 |
| 중앙 | 공지, 남은 시간, 진행 막대, 현재 차례, 숫자 입력 |
| 아래 왼쪽 | 숫자 판정 결과와 채팅 기록 |
| 아래 오른쪽 | 일반 채팅 입력 |

1600×900을 기준으로 배치하고 ScaleBox로 화면 비율에 맞춰 조절했습니다. 어두운 배경 위에 밝은 글자를 사용하고, 점수와 시간은 크게 표시했습니다.

### 5-4. 연결 종료와 새 연결

경기 중 한 명이 나가 참여자가 두 명 미만이 되면 턴을 멈추고 준비 상태로 돌아가도록 처리했습니다. 남아 있는 플레이어의 승수와 사용 횟수, 진행 중인 라운드의 정답은 유지했습니다.

새 플레이어가 접속한 뒤 모두 준비하면 진행 중이던 라운드를 재개하도록 구현했습니다. 퇴장자를 서버의 참여 목록에서 제거해 이후 턴과 종료 판정에 포함되지 않도록 처리했습니다.

## 7. 구현 중 해결한 문제

### 서버와 클라이언트의 상태 일치

숫자 판정, 기회 차감, 승리 처리를 서버에서 수행하도록 모았습니다. 클라이언트가 결과를 직접 결정하지 않고, 복제된 상태와 RPC 메시지를 받아 화면을 갱신하도록 역할을 정리했습니다.

### 시간 초과 직전 입력과 늦은 요청

입력이 도착한 시점에 서버의 마감 시각을 확인했습니다. 이미 지난 턴이나 라운드의 요청은 번호 비교로 걸러냈으며, 종료 상태 검사와 타이머 정리를 함께 적용해 기회 차감 및 라운드 종료의 중복 처리를 방지했습니다.

### 라운드 초기화 범위

초기화할 값과 유지할 값을 구분했습니다. 새 라운드에서는 정답·시도 횟수·준비 상태를 갱신하고, 연결 중인 플레이어의 이름·누적 승수·채팅 기록은 유지하도록 구현했습니다.

### 배경 이미지와 실제 UI 배치

배경 이미지 위에 이름, 점수, 시간, 입력창이 겹치지 않도록 영역을 나누었습니다. 두 클라이언트가 각각 자신을 왼쪽에 표시하도록 구성하고, 준비·진행·결과 상태에 맞게 버튼과 안내를 갱신했습니다.

## 9. 현재 구현 범위

- 기본 UI는 두 플레이어의 대결에 맞췄습니다. 서버의 준비·턴 처리는 접속한 참여자를 대상으로 하지만, 전광판 상대 패널에는 한 명만 표시합니다.
- 누적 승수는 연결 중 라운드 사이에 유지됩니다. 계정별 저장이나 재접속 시 기록 복원은 구현하지 않았습니다.
- 연결 종료로 일시 정지한 뒤 재개하면 새 턴 시간을 부여합니다. 중단 직전 남은 시간을 복원하는 방식은 아닙니다.
- 서버 시간 동기화 직후에는 클라이언트의 남은 초 표시가 잠시 차이 날 수 있으며, 최종 입력 허용 여부는 서버가 판정합니다.
- 저장된 검증은 로컬 서버·클라이언트 환경에서 수행한 결과입니다. 인터넷 환경의 지연·패킷 손실 및 배포용 패키지 검증은 별도 범위입니다.
